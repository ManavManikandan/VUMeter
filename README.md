# VUMeter
# ESP32 Bluetooth LED VU Meter
 
An ESP-IDF project that turns an ESP32 into a discoverable Bluetooth Classic audio sink. Any phone or laptop can pair with it as "ESP32-SPEAKER" and stream audio over A2DP. The incoming PCM stream is analyzed in real time and displayed as an RMS volume meter on the serial console.
 
**Note:** this is currently an *analysis-only* sink — there's no I2S DAC output wired up yet, so audio comes in and gets measured but isn't played back out loud. It's set up as the front-end for an audio-reactive project (LED visualizer, mood lamp, etc.) rather than as an actual speaker replacement.
 
## What it does today
 
- Advertises as **`ESP32-SPEAKER`**, discoverable and connectable
- Pairs with **Just Works** SSP (no PIN prompt)
- Accepts A2DP audio streams (16-bit signed PCM)
- Computes RMS on every 5th received buffer and prints a 50-char volume bar to the serial console:
```
  Vol: [############                                      ]
```
- Re-enables discoverability automatically on disconnect so you don't have to power-cycle to pair a new device
## Hardware
 
- Any ESP32 with Bluetooth Classic support (**ESP32**, not ESP32-S2/S3/C3 — those don't have Classic BT).
- USB cable for programming and the serial monitor.
That's it — no external components required for the current functionality.

## Prerequisites
 
- **ESP-IDF v4.4 or newer** (tested on v5.x). Install per [Espressif's docs](https://docs.espressif.com/projects/esp-idf/en/latest/esp32/get-started/index.html).
- Python 3.8+
- A USB-to-serial driver appropriate for your dev board (CP210x, CH340, etc.)
## Build and flash
 
```bash
# One-time: set target chip
idf.py set-target esp32
 
# Configure Bluetooth (see menuconfig notes below)
idf.py menuconfig
 
# Build, flash, open serial monitor
idf.py build
idf.py -p /dev/tty.usbserial-XXXX flash monitor
```
 
Exit the monitor with `Ctrl-]`.
 
### Required menuconfig settings
 
The A2DP sink pulls in a lot of the BT stack that ESP-IDF doesn't enable by default. Under `Component config → Bluetooth`:
 
- **Bluetooth** → enabled
- **Bluetooth controller** → mode set to **Bluetooth Dual Mode (BTDM)** *(the code calls `esp_bt_controller_enable(ESP_BT_MODE_BTDM)` and will fail with "Invalid Arg" if the controller isn't compiled for dual mode)*
- **Bluedroid Options** → enabled
  - **Classic Bluetooth** → enabled
  - **A2DP** → enabled
  - **SPP** → optional, off is fine
If you skip these you'll get link-time errors on `esp_a2d_sink_init` and friends.
 
## How to use it
 
1. Flash, then open the serial monitor. You should see:
```
   Bluetooth Started! Name: ESP32-SPEAKER
```
2. On your phone/laptop, open Bluetooth settings and pair with **ESP32-SPEAKER**. No PIN needed.
3. On successful pair the monitor prints:
```
   authentication success: <your device name>
   Bluetooth Device Connected!
```
4. Start playing audio and route it to the ESP32. The volume bar should start moving with the music.
5. Disconnect from the phone, and the ESP32 automatically becomes discoverable again for the next device.
## Code walkthrough
 
Three callbacks do the work:
 
- **`bt_app_gap_cb`** — handles GAP events (pairing, auth). Right now it only prints on `ESP_BT_GAP_AUTH_CMPL_EVT`.
- **`bt_app_a2d_cb`** — handles A2DP connection state changes. On disconnect, it re-arms discoverability via `esp_bt_gap_set_scan_mode`.
- **`bt_app_a2d_data_cb`** — receives the PCM audio buffer. Every 5th call it treats the buffer as `int16_t` samples, computes `sqrt(mean(x^2))`, normalizes by 32768, scales to 0–50, and redraws the bar in place using `\r`.
The RMS throttling (`count % 5`) is important — the callback fires often enough that printing on every buffer will back up the UART and stutter the audio processing.
 
## What I'd add next
 
- **I2S output** to a MAX98357A or PCM5102 DAC — turn it into a real speaker. Push `data` straight into `i2s_write` inside the A2DP data callback.
- **AVRC (remote control)** so play/pause/next on the phone works and the ESP32 can read track metadata.
- **LED strip driver** (WS2812B via RMT or FastLED-equivalent) fed by the RMS value for an audio-reactive visualizer — this is what the project is really pointed at.
- **FFT instead of RMS** if the visualizer wants per-band response (bass / mids / highs) rather than just an envelope.
- **NVS-backed device name** so it can be renamed without re-flashing.
